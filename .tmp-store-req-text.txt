1. Project Overview
Build a merchandise store as one more module of usclt20.com. Visitors browse team-wise products such as jerseys, add items to a cart, sign in or sign up at checkout, save delivery addresses, pay through the existing Cashfree integration and track their orders. Administrators run the whole store from a new Store Settings section of the existing admin panel.
Product, price, size, stock, coupon, delivery and GST changes made by the administrator must show on the storefront through the application, without any frontend code change.
1.1 Goals
Let anyone browse active products grouped by team.
Let shoppers filter the list; show everything until a filter is applied.
Let customers sign up with minimal details, save addresses and view their orders.
Calculate subtotal, coupon discount, delivery fee, GST and payable total on the server.
Give administrators full control of products, orders, coupons, delivery fee and GST.
Leave all existing USCL flows and functionality untouched.

3. Users and Permissions
3.1 Visitor
Browse active products, filter by team, size and price, view product details and the cart.
Must sign in or sign up to complete checkout (guest checkout is not offered).
3.2 Store Customer
A shopper with a store account. This covers two kinds of people: registered players who log in with their existing credentials, and other people who sign up on the store.
A person who signs up on the store is only a store user. They are not a player and get no player features.
Can manage own saved addresses, place orders, use coupons and view and download own invoices.
3.3 Registered player (existing, unchanged)
Player registration and player login keep working exactly as today. A player who already has credentials uses them to log in to the store, and the store links that player to a store customer record for orders and addresses. A player who has no credentials signs up as a store user like anyone else.
3.4 Administrator
Uses the existing admin login. Access to Store Settings is controlled by a role/permission (for example &quot;Manage Store&quot;).
Manages products, orders, coupons, delivery fee, GST and store customers.
Important changes are recorded in an audit log.
4. Isolation From Existing USCL Functionality
All new database tables use a store_ prefix. No existing table is altered. Teams and player credentials are only read.
Player credentials are only checked, never changed. The store has its own session, separate from the player and admin sessions.
New routes live under their own path (for example /store and /api/store). Existing routes are not changed.
The only edits to existing files are the Store menu link on the website and the Store Settings menu in the admin panel.
Cashfree: reuse the existing client or helper. Store payments use their own order reference prefix and their own webhook handler (or a clearly separated branch) so player payments are unaffected.
Ship behind a feature flag so the module can be switched off without a code rollback.
Regression check before release: player registration, player login, team and match pages and existing payments.

5.6 Dynamic search
A search box in the store header and on the store page finds products as the customer types. It must feel instant and forgiving.
Behaviour
Detail
As you type
After 2 characters, with a short delay (about 250 ms) and cancellation of the previous request, a suggestion list opens under the box. The product list below updates without reloading the page.
Suggestion groups
Brands, Teams, Products (thumbnail, name, product code, price) and exact product-code matches.
What is searched
Product name, product code, size code, brand, team and description (description counts less).
Spelling tolerance
Text is normalised (case, spaces, punctuation). Matching uses prefix match, word match and fuzzy match that allows one wrong, missing or extra letter in short words and two in longer ones. Example: typing &quot;adididas&quot; suggests the brand Adidas, and &quot;chicgo&quot; suggests Chicago.
Brand and team shortcut
If the typed text matches or nearly matches a brand or team, it is the first suggestion (for example &quot;Brand: Adidas&quot;). Choosing it applies that filter and shows all of its products.
Did you mean
If nothing matches exactly, the page shows results for the closest match with a line such as &quot;Showing results for Adidas&quot;.
Ranking
Exact product code first, then exact brand, team or name, then names that start with the text, then names that contain it, then fuzzy matches. In-stock items rank above out-of-stock items.
With filters
Search and filters work together. Search for &quot;jersey&quot; and filter by team and size at the same time.
No results
A friendly message with popular brands and teams to try.
Keyboard and touch
Arrow keys, Enter and Escape on desktop. Large tap targets on mobile.
Speed target
Suggestions in about 200 ms and full results in about 500 ms for the expected catalogue size. Measure this in testing.
How it is made fast
Each product keeps a normalised search text (name, code, size codes, brand, team). It is indexed and rebuilt automatically whenever a product, brand or team changes, so search is never out of date.
A small cached list of all brand, team and product names is used to correct the typed text. This list is tiny, so fuzzy matching on it is very quick. The corrected terms then go to an indexed database query, which avoids slow scans of the full table.
Only the fields needed for the list are returned, with small thumbnails, in pages of results.
Popular suggestions and recent queries are cached for a short time.
If the catalogue stays small (a few hundred products), a compact search index can be sent to the browser once for instant results. A separate search engine is needed only if the catalogue grows very large. Confirm the approach after the database audit.
Search input is always sent as a safe parameter, the suggestion endpoint is rate limited, and the storefront only searches active products.
5.7 Segregation by team, brand and size
The filter panel has three groups: Team, Brand and Size, plus price range. All options come from admin data, so new teams, brands and sizes appear without code changes.
Inside one group the choices are OR (Chicago or California). Between groups they are AND (team and brand and size).
Each option shows how many products match it, and options with none are greyed out.
The page address keeps the chosen filters and search text, so a filtered list can be bookmarked, shared or reloaded.
Clearing the filters returns to the full list of products.
The admin product list has the same Team, Brand and Size filters (section 6.1).

7.3 Saved addresses and default address
Fields: recipient name, mobile, address lines, landmark (optional), city, state, PIN/postal code and country.

8. Cart and Checkout
8.1 Checkout steps
Cart holds product, size and quantity. The cart is kept for logged-in customers and in the browser session for visitors, then merged at login.
Prices shown are read from the database. The browser never supplies a trusted price.
Every line in the cart and at checkout shows the image, name, product code, size code, size, quantity and price, so items are easy to identify.
Steps: sign in or sign up, choose or add address, apply coupon, optional GST number (when the bill type is GST bill), review price breakup, pay.
Repeated clicks or retries must not create duplicate orders (use an idempotency key).
8.2 Server re-verification when Pay is clicked
The checkout screen total is only a preview. When the customer clicks Pay, the server ignores every amount from the browser and builds the order again from scratch. Only product IDs (or size codes), quantities, the coupon code, the chosen address and the GST number are accepted from the browser.
Step
Server check
1
Load each product and size by ID and size code. Reject inactive, archived or unknown items.
2
Check stock for each size and quantity. Reject if the quantity is more than the stock left.
3
Read the current price from the database and compute the item subtotal.
4
Re-validate the coupon or offer (dates, once per user, minimum order, eligibility) and compute the discount from the subtotal.
5
Compute the delivery fee from the backend settings (free at or above the threshold).
6
Compute GST by delivery state (Telangana: CGST and SGST; other states: IGST) and apply the billing mode from admin.
7
Compare the new total with the total shown to the customer. If it differs, stop, show the updated total and ask the customer to confirm. Never charge a different amount silently.
8
Create the order with the server-calculated total, reserve the stock and the coupon, and create the Cashfree order for exactly that amount.
9
When payment is reported, compare the amount paid with the stored order total. A mismatch is flagged for the admin and the order is not marked paid.
8.3 Payment modes (backend setting)
Store Settings has a Payment Modes screen where the admin switches modes on or off. The checkout shows only the modes that are on.
Cashfree online payment is the main mode and uses the existing integration.
Cash on delivery can be added as a mode and is off unless the admin turns it on. Confirm whether it is needed at launch.
The selected mode is validated on the server again when Pay is clicked.

11. GST (Handled in Admin)
The business is registered for GST in Hyderabad, and the registered state is Telangana. Everything about GST is configured and managed by the administrator. Customers only see the result on the price breakup and the invoice.
11.1 GST Settings (admin)
Setting
Detail
Business details
Legal name, GSTIN, registered address and state (Telangana). Shown on invoices.
Bill type
GST bill or normal bill. Chosen by the admin and applied at checkout (see 11.3).
Price basis
Whether product prices include GST or exclude GST (store-wide setting, with per-product override if needed).
HSN code and rate per product
Set on each product. Default values can be set in GST Settings. The accountant decides the codes and rates, and the admin can change them when rules change.
Delivery fee tax treatment
Whether GST applies to the delivery fee and at which rate. Confirm with the accountant.
Invoice numbering
Financial-year based, continuous series with a configurable prefix (for example USCL/2026-27/0001).
Effective dates
Rate changes apply from a date and never rewrite past orders.
11.2 Calculation rules
Place of supply is taken from the delivery state. If it is Telangana, GST is split into CGST and SGST. For any other Indian state, IGST is charged.
GST is calculated per line using the product rate and then totalled. Amounts use paise (integers) with one consistent rounding rule.
Each order stores a snapshot: GST rate, HSN code, taxable value, CGST, SGST or IGST amounts and the GST settings in force.
Customers see subtotal, discount, delivery fee, GST and total as separate lines.
Confirm with the accountant: treatment of orders delivered outside India. The league has US teams, and GST rules differ for exports. If deliveries outside India are planned, a country-wise rule is needed before launch.
11.3 Bill type: GST bill or normal bill
In GST and Billing, the admin sets the bill type. Checkout applies the chosen type to new orders. Past orders keep the type they were created with.
GST bill: shows the business GSTIN, invoice number, HSN codes, taxable value and the CGST, SGST or IGST split.
GST bill with customer GST number: when the bill type is GST bill, checkout offers an optional &quot;GST number&quot; field. If filled, the bill also shows the customer&apos;s GSTIN and business name. The number is checked for the 15-character GSTIN format.
Normal bill: a simple bill with items, discount, delivery fee and total, without a tax breakup. Confirm with the accountant that a normal bill is allowed, because the business is GST-registered and taxable sales normally need a tax invoice.
11.4 Invoices and reports
An invoice is created for each paid order. The customer can view it on screen and download it as a PDF from My Orders. The admin can do the same from the order detail.
Invoice numbers follow the financial-year series set in GST Settings.
Each invoice line shows the product code, size code, size and quantity.
Credit note for cancelled or refunded orders.
Admin reports: sales by period, GST collected (CGST, SGST, IGST), HSN-wise summary, with CSV/Excel export for the accountant.
12. Payment (Cashfree)
Reuse the existing Cashfree integration after reviewing it. Do not create a second gateway setup.
The server creates the Cashfree order using the server-calculated total and a unique store order reference.
Payment is confirmed only by server-side verification with Cashfree or a verified webhook. A browser redirect alone never marks an order paid.
Handle success, failure, pending, cancelled, duplicate and delayed notifications. Webhook processing is idempotent.
Store Cashfree order and payment references, amount, status and timestamps. Never store card data.
Retry path for failed or abandoned payments. Test in sandbox before production.
The payment modes shown at checkout follow the backend Payment Modes setting (section 8.3).

Admin (Store Settings): product list and product/image CRUD, brands CRUD, size and stock update, orders list/detail/status/invoice/export, coupon CRUD and reports, delivery settings, payment modes, GST and billing settings and reports, customers list, policies.
Every private route checks authorisation on the server. Admin routes check the Store permission. Customer routes check ownership of the record.
15. Price Calculation Order
Step
Action
1
Validate each product, size and quantity, and read the current price from the database.
2
Compute the item subtotal.
3
Validate the coupon and compute the discount (once per user, minimum order, maximum discount).
4
Compute the delivery fee: zero if the amount reaches the free-delivery threshold, else the configured fee.
5
Compute GST per line (CGST+SGST for Telangana, IGST for other states), and on the delivery fee if configured.
6
Return the full breakup and the payable total as a preview.
7
When Pay is clicked, repeat steps 1 to 5 on the server (section 8.2) and use only the new result for the order and the Cashfree amount.
16. Security and Reliability
Validate and sanitise all inputs; rate limit login, sign up, coupon, search suggestion and checkout endpoints. Search text is always passed as a safe parameter.
Never trust prices, discounts, stock, GST or payment status sent from the browser.
Verify Cashfree webhook signatures; keep secrets in server configuration. Compare the amount Cashfree reports with the stored order total before marking an order paid.
Restrict image uploads and block script execution in storedata.
Customers cannot read another customer&apos;s orders, addresses or coupon history.
Log admin changes and payment events without storing sensitive payment data.
Include the store tables and webroot/storedata in backups.
